# FinalRun Architecture (Phase 2)

This document describes the scene tree, synchronization rules, instance isolation, and transfer flow
of the core systems defined in `docs/BRIEF_core_systems.md`.

## 1. Overview

FinalRun is a 3D multiplayer extraction crime sandbox built on Godot 4.7 and ENet.
One dedicated server process is one "big server" with an id of the form `SV-SPACE-XXXX`
(generated by `ServerManager.generate_server_id()` at server start and stored in `server_id`).

A big server hosts 4 maps:

| Map | Kind | Capacity | Purpose |
|---|---|---|---|
| `Motel` | instanced (`Motel-01`, `Motel-02`, ...) | 16 | Safezone, cash stash, party creation (max 3) |
| `LootyBay` | instanced (`LootyBay-01`, ...) | 12 | PvPvE heists, has `ExtractZone` and `PoliceStation` |
| `House` | shared (`House`) | `MAX_CLIENTS` | Housing, storage, laundering desk; everyone sees each other |
| `Center` | shared (`Center`) | `MAX_CLIENTS` | Market, sell loot, trade, upgrade |

Instanced maps are created on demand and freed after staying empty for 60 seconds
(`EMPTY_INSTANCE_FREE_SECONDS`). `House` and `Center` are created at server boot and never destroyed.

The server is authoritative for everything: role, damage, loot, transfers, parties, and instance membership.
Clients only send requests through RPCs declared `@rpc("any_peer", "call_remote", "reliable")`,
and the server checks `multiplayer.get_remote_sender_id()` on every call.

`autoload/ServerManager.gd` is a thin autoload and RPC entry point. Its runtime state lives in
`RefCounted` services created by the autoload (no extra autoloads):

| Service | Owns |
|---|---|
| `features/instance/InstanceRegistry.gd` | create/find/free instances, `select_instance`, `format_instance_id`, empty-instance timer, slot reservations, peer → instance mapping, spawning and visibility |
| `features/party/PartyService.gd` | create, invite/accept, leave, kick, pending invites, leader rules |
| `features/transfer/TransferService.gd` | allowed routes (`is_route_allowed`), transfer state, ack wait, timeout, disconnect cleanup, LootyBay party entry |
| `features/player/PlayerService.gd` | connection state, custom spawn, sell/mask/cop duty, combat, surrender, death, extraction and zones |
| `features/downed/DownedService.gd` | bleed-out tick, revive/finish/cuff/search rules, body containers and open search sessions |

`ServerManager` keeps the fixed RPC method names and node path, validates senders, and forwards to
these services. Cross-service helpers with no project imports live in `lib/`
(`GameConst`, `NetUtil`, `ItemUtils`).

## 2. Scene tree

### 2.1 Dedicated server

```text
/root
├── ServerManager                  (autoload, Node)
└── Main                           (main/Main.tscn, Node)
    └── Instances                  (Node)
        ├── House                  (SubViewport, own_world_3d = true, UPDATE_DISABLED)
        │   ├── Map                (maps/house/House.tscn)
        │   │   └── SpawnPoints/Marker3D ...
        │   ├── Players            (Node3D)
        │   ├── Drops              (Node3D)
        │   └── Spawner            (MultiplayerSpawner, spawn_path = ../Players)
        ├── Center                 (SubViewport)
        │   └── ... same layout as House
        ├── Motel-01               (SubViewport)
        │   └── ...
        └── LootyBay-01            (SubViewport)
            ├── Map
            │   ├── ExtractZone    (Area3D)
            │   ├── PoliceStation  (Area3D)
            │   ├── PoliceVehicle  (Node3D, placeholder)
            │   └── SpawnPoints/Marker3D x12
            ├── Players
            ├── Drops
            └── Spawner
```

Every instance root is a `SubViewport` with `own_world_3d = true` and `disable_3d = false`,
so physics spaces are truly separate, while rendering is turned off on the server with
`render_target_update_mode = SubViewport.UPDATE_DISABLED`.

### 2.2 Client

The client holds only its current instance. The `Instances` node of `Main` becomes a
`SubViewportContainer` with `stretch = true` covering the full screen, and the instance
`SubViewport` is its direct child.

```text
/root
├── ServerManager                  (autoload, Node)
└── Main                           (Node)
    └── Instances                  (SubViewportContainer, stretch = true, full rect)
        └── Motel-01               (SubViewport, own_world_3d = true, UPDATE_ALWAYS)
            ├── Map                (instance of maps/motel/Motel.tscn)
            ├── Players            (Node3D)
            ├── Drops              (Node3D)
            ├── Spawner            (MultiplayerSpawner, spawn_path = ../Players)
            └── ClientCamera       (Camera3D)
```

The instance root path is identical on both sides:

```text
/root/Main/Instances/<instance_id>
```

So RPCs, `MultiplayerSpawner`, and `MultiplayerSynchronizer` resolve the same path on server and
client, even though the client wraps it in a `SubViewportContainer`.

## 3. Instance isolation (core requirement)

1. **One World3D per instance.**
   Every `SubViewport` sets `own_world_3d = true`, giving each instance its own `World3D` and physics
   space. Raycasts, bullets, and interactions cannot cross instances.
   Never set `disable_3d = true` on the server (physics needs the world); only rendering is disabled.

2. **One `MultiplayerSpawner` per instance.**
   The spawner lives at `/root/Main/Instances/<instance_id>/Spawner` with `spawn_path = ../Players`.
   Players are spawned only through a custom `spawn_function`, never with a manual `add_child()`.

3. **Synchronizer visibility hides players across instances.**
   `Player.tscn` has a `MultiplayerSynchronizer` under its root with `public_visibility = false`.
   The server grants visibility with `set_visibility_for(peer_id, true)` only to peers in that
   instance's `members`, and calls `Instance.refresh_visibility()` whenever someone joins or leaves.

   Godot only sends spawns and sync data for spawner-created nodes to peers that can see the node's
   synchronizer, so players in other sub-sessions never see each other.

4. **No broadcast `rpc()` for gameplay events.**
   `lib/net/NetUtil.gd` implements the dispatch loop. `Instance.rpc_to_members()` and
   `Instance.rpc_to_specific_members()` are thin wrappers that pass the instance member list, so
   packets go only to that instance's members (plus per-peer filtering, e.g. loot alerts sent only
   to `COP` and `CRIMINAL`).

5. **Every request validates its sender.**
   Every server RPC starts with `multiplayer.get_remote_sender_id()`, and the peer must exist in
   `_player_states` (connected and joined). The player is then resolved only from the sender's own
   instance. If the sender is not a member of the instance that owns the target node, the request is
   rejected (e.g. `server_request_attack()` only looks for targets in the shooter's `Players` node).

6. **Server-side hit detection.**
   Shots and LOS checks run in `from_player.get_world_3d().direct_space_state` with
   `PhysicsRayQueryParameters3D` and collision mask `3` (world + players), so the raycast only ever
   hits the shooter's own sub-world.

## 4. Synchronization and RPC

### 4.1 Player synchronizer

The player's `MultiplayerSynchronizer` replicates these properties (declared through a
`SceneReplicationConfig` sub-resource inside `Player.tscn`, so it exists before the spawner starts
replication):

| Property | Purpose |
|---|---|
| `.:peer_id` | Tells the client which peer owns this node; enables input only on the owner's machine |
| `.:role` | Syncs `CITIZEN` / `CRIMINAL` / `COP` to clients |
| `.:life_state` | Syncs `ALIVE` / `DOWNED` / `DEAD` to clients |
| `.:downed_deadline_ms` | Unix-ms bleed-out deadline; the client computes the remaining seconds |
| `.:position` | Server-owned position |
| `.:rotation` | Server-owned rotation |

`PlayerRoleController` owns the role and life rules, but the replicated values are stored on
`Player.role` / `Player.life_state` so the synchronizer at the root of `Player.tscn` can replicate
them directly. The controller reads and writes through those properties once bound to a player
(with a standalone fallback for unit tests). `life_state` is not part of `export_state()`:
`setup_server()` always starts a fresh node `ALIVE` with full HP.

### 4.2 Custom spawn on both sides

`MultiplayerSpawner.spawn_function` runs on **every peer** that receives the spawn, so it must be set
on both server and client:

- Server: `PlayerService.spawn_node()` → `Player.setup_server(instance, state)`
- Client: same function; when `multiplayer.is_server() == false` it calls
  `Player.setup_client(instance)` to bind the controller context
- Both sides receive the function through `ServerManager.configure_spawner()`, which delegates to
  `InstanceRegistry`; the client calls it from `Main.client_show_instance()` after `Instance.setup()`
- Inventory, notoriety, and cash are not included in the spawn payload; they stay on the server

### 4.3 Granting visibility

When a player enters an instance:

1. `Instance.add_member(peer_id)`
2. Spawn the player through the spawner
3. `Instance.refresh_visibility()`: for every connected peer, call
   `sync.set_visibility_for(peer, members.has(peer))` on every player in the instance
4. `Instance.sync_state_to_peer()`: send the current `PoliceVehicle` and `LootDrop` state to the
   newly joined client (visibility does not replay past events)

When a player leaves an instance:

1. `InstanceRegistry.revoke_visibility()` (via `NetUtil.revoke_visibility()`) sets
   `set_visibility_for(..., false)` both for the leaving player's node and for every other player's
   synchronizer toward the leaving peer
2. Despawn / `queue_free()` the player node
3. `Instance.remove_member(peer_id)` and `refresh_visibility()` again

## 5. Transfer flow

Every map change follows the same path, including the first join.

```text
Client                                Server
  |                                      |
  |                                      | validate route / party / capacity
  |                                      | reserve slot in target instance
  |                                      | snapshot state from controller
  |                                      | despawn player from old instance
  |                                      | revoke visibility
  |  <------ client_load_instance(id,map)|
  |  build new SubViewport at same path  |
  |  set spawner spawn_function          |
  |  ----- client_instance_ready(id) --->|
  |                                      | spawn player at SpawnPoints
  |                                      | add_member + refresh_visibility
  |  <------ custom spawn + sync ---------|
```

Details:

- `TransferService._transfers[peer_id]` stores `target_id`, `map_name`, `deadline_ms`
- The target instance increments `reserved_slots` while waiting for the ack, so the room cannot fill up mid-transfer
- Before despawn, the server calls `controller.server_prepare_leave_instance()` (cancels the mask
  channel, goes off duty if `COP`), then `export_state()` saves role, `loot_bag`, `equipped_gear`,
  `saved_civilian_gear`, `notoriety`, `cash`, `cop_on_duty`
- The server waits for `client_instance_ready()` at most `TRANSFER_TIMEOUT_SECONDS` (10 s); on timeout
  it releases the reservation and disconnects the peer
- If the peer disconnects at any step, `ServerManager.handle_peer_left()` delegates to
  `PlayerService.handle_peer_left()`, which clears the transfer, reservation, instance membership,
  party and state (resolving a downed body's death and LootDrop before despawn)
- The client builds the new instance before acking, and the server spawns only after the ack, so the
  destination spawner and synchronizer exist when the spawn message arrives

### 5.1 Allowed routes

| From | To |
|---|---|
| `Motel` | `LootyBay`, `House`, `Center` |
| `House` | `Motel`, `Center` |
| `Center` | `Motel`, `House` |
| `LootyBay` | Exit only via `ExtractZone`, death, or surrender (to `Motel`) |

`TransferService.is_route_allowed()` is a pure static function, testable without a network.

### 5.2 Instance selection

`InstanceRegistry.select_instance(candidates, party_size)` picks an instance with
`capacity - used >= party_size`, preferring the fullest one that still fits, to keep rooms full.
If none fits it returns `""` and the caller creates a new instance
(names like `Motel-01`, `LootyBay-03` come from `InstanceRegistry.format_instance_id()`).

## 6. Party

`features/party/Party.gd` is a plain `RefCounted` holding `id`, `leader_id`, `members: Array[int]`,
and enforces `MAX_MEMBERS` from `GameConst.PARTY_MAX_MEMBERS` (3) itself.
`features/party/PartyService.gd` owns the registry and network-facing party flow.

- Create: `server_request_party_create`
- Invite / accept: `PartyService` keeps `_pending_invites`; an invite becomes invalid if the party is
  disbanded or its id changes
- Leave: if the leader leaves, `Party.remove_member()` passes leadership to the first remaining member
- Kick: leader only, and the leader cannot kick themselves
- Disconnect: `ServerManager.handle_peer_left()` → `PartyService.remove_peer()` removes related
  invites and leaves the party

Entering `LootyBay`:

- In a party, only the leader can trigger it
- All members must be in `Motel` and none may be mid-transfer
- The whole party moves together, using the party size as `party_size` for instance selection
- If no instance fits everyone, a new `LootyBay` is created

Moves to `Motel`, `House`, and `Center` are individual (the party does not follow, since those maps are
not a shared heist run).

## 7. Roles and combat

`PlayerRoleController` defines `enum Role { CITIZEN, CRIMINAL, COP }` and the signal
`role_changed(old, new)`.

### 7.1 Mask

- Requestable only in `LootyBay`, only as a live `CITIZEN`
- Starts a 3 s channel on `lib/components/ChannelTimer.gd` (`MASK_CHANNEL_SECONDS`)
- Cancelled with one of four reasons: `moved` (more than `MASK_MOVE_CANCEL_DISTANCE`),
  `damaged`, `left_instance`, or `invalid_state` (role/life changed)
- On completion the controller re-checks state before becoming `CRIMINAL`
- `CRIMINAL → CITIZEN` happens only through successful extraction, surrender, cuff, or death; there
  is no request to remove the mask manually

### 7.2 Cop

- Go on duty only inside the `LootyBay` `PoliceStation`, and only as `CITIZEN`
- On duty: civilian gear is stored in `_saved_civilian_gear`, the `COP_LOADOUT` items are issued
  (`issued: true`) with their own uids, role becomes `COP`, and the instance's `PoliceVehicle`
  placeholder is enabled
- Going off duty requires being in the `PoliceStation` (except when forced by extraction or death);
  civilian gear is restored and the role returns to `CITIZEN`
- A party cannot mix roles: mask is rejected if any member is `COP`, cop duty is rejected if any
  member is `CRIMINAL` (`PlayerService.party_role_conflict`)

### 7.3 `can_attack` matrix

`can_attack_roles(attacker_role, target_role, map_name, safezone, same_party = false)` is a pure
static function. `same_party` is appended last, so existing callers keep the old behavior; passing
`true` returns `false` (party friendly fire is off, which also blocks finish-off by teammates).

| Attacker | Target | Result |
|---|---|---|
| `CITIZEN` | anyone | `false` |
| `CRIMINAL` | `CITIZEN` | `false` |
| `CRIMINAL` | `CRIMINAL` | `true` |
| `CRIMINAL` | `COP` | `true` |
| `COP` | `CRIMINAL` | `true` |
| `COP` | `COP` | `false` |
| `COP` | `CITIZEN` | `false` |
| anyone | anyone | `false` in `Motel` (safezone), `House`, `Center` |

The controller's `can_attack(target, same_party = false)` uses this static function with the instance
context. `PlayerService.attack()` (called by `ServerManager.server_request_attack()`) computes
`same_party` from the party service and checks instance membership, range, `can_attack()`, and
raycast LOS before calling `target.take_damage()`. All rule constants come from
`lib/constants/GameConst.gd`.

### 7.4 Life state and downed actions

`PlayerRoleController` owns `enum LifeState { ALIVE, DOWNED, DEAD }` and the signal
`life_state_changed(old, new, cause)`. `server_set_life_state(new_state, cause, now_ms)` is the only
writer; it is idempotent and validates the cause (`damage`, `bleedout`, `finish`, `disconnect`,
`redown`, `revive`, `cuff`, `respawn`). All server time comparisons take an injected `now_ms`; the
source is `int(Time.get_unix_time_from_system() * 1000.0)`.

| Transition | Rule |
|---|---|
| `ALIVE → DOWNED` | 0 HP in `LootyBay`; deadline = now + `DOWNED_BLEEDOUT_SECONDS` |
| `ALIVE → DEAD` | 0 HP outside `LootyBay`, or a re-down inside `REDOWN_WINDOW_SECONDS` |
| `DOWNED` + damage | HP stays 0, deadline moves back `DOWNED_HIT_PENALTY_SECONDS`; at/after deadline → `DEAD` (`bleedout`) |
| `DOWNED → DEAD` | bleed-out, finish-off, or disconnect |
| `DOWNED → ALIVE` | revive: party member, same role, one reviver; `REVIVE_HP_RATIO` HP |
| `DOWNED → ALIVE` (cuff) | COP arrest: surrender outcome, citizen, transferred to Motel, never DEAD |

A downed player crawls at `DOWNED_CRAWL_SPEED` and cannot attack, mask, take cop duty, surrender,
join a map or extract. `setup_server()` always starts a fresh player `ALIVE` with full HP.

`features/downed/DownedService.gd` is a `RefCounted` service owned by `ServerManager`. It owns no
Nodes: channels are `ChannelTimer` nodes parented under the acting player, and body search lists are
`LootContainer` nodes parented under the downed player. `ServerManager._process` calls
`DownedService.tick(now_ms)` for bleed-out and to close search sessions whose range, LOS or
permission no longer holds.

`lib/components/ChannelTimer.gd` is the shared hold-interact node:

```gdscript
start(duration: float, actor: Node3D, max_move: float, cancel_check: Callable)
cancel(reason: String)
signal completed
signal cancelled(reason: String)
```

`cancel_check()` returns `""` or one of `moved`, `out_of_range`, `no_los`, `damaged`, `disconnected`,
`target_state`, `actor_state`, `left_instance`, `invalid_state`. On `completed` the owner re-checks
permission and target state before applying anything, so the first finished timer wins.

#### Downed RPCs

All are `@rpc("any_peer", "call_remote", "reliable")` on `ServerManager`, validate
`multiplayer.get_remote_sender_id()` with `_can_accept_alive_request`, and delegate to
`DownedService`:

| RPC | Action |
|---|---|
| `server_request_revive(target_peer_id)` | `REVIVE_SECONDS` channel |
| `server_request_finish(target_peer_id)` | `FINISH_SECONDS` channel |
| `server_request_cuff(target_peer_id)` | `CUFF_SECONDS` channel |
| `server_request_search_open(target_peer_id)` | `SEARCH_OPEN_SECONDS` channel |
| `server_request_search_take(target_peer_id, item_uid)` | take/seize one item, re-check everything |
| `server_request_search_close(target_peer_id)` | close the viewer's session |

Server-to-client replies are `client_search_contents(target_peer_id, items)` and
`client_search_closed(target_peer_id, reason)`; both use `NetUtil.rpc_to_peer`, and contents go only
to the viewer (updates only to open viewers). `server_request_move` remains allowed while downed so
the body can crawl at `DOWNED_CRAWL_SPEED`; a `DEAD` player's speed is zero.

Every other request in spec §7 is gated by `_can_accept_alive_request`: attack, mask, cop duty,
surrender, join map, sell loot, party create/invite/accept, and all six downed requests.

## 8. Inventory, notoriety, and ending a run

`PlayerRoleController` stores:

```gdscript
var loot_bag: Array[Dictionary] = []        # {uid, id, value, issued}
var equipped_gear: Array[Dictionary] = []   # {uid, id, value, issued}
var notoriety: float = 0.0
var cash: int = 0
```

The server-wide uid counter (`_next_item_uid`) lives in `PlayerService`; `lib/utils/ItemUtils.gd` is
stateless (`make_item`, `find_by_uid`, `remove_by_uid`, `lootable_only`). Items that arrive without a
uid in a transfer snapshot receive one in `apply_state()`. The `source` tag (`bag` / `gear`) is added
only while an item is listed for a search and is never stored in an inventory.

- `grant_loot(id, value)` adds one `ItemUtils.make_item` entry and raises notoriety by its value;
  `grant_gear(id, value)` adds gear without notoriety
- `receive_item(item, source)` transfers an item and keeps its uid (bag items raise notoriety)
- `remove_item_by_uid(uid)` removes from bag or gear and lowers the owner's notoriety by the value,
  clamped at 0
- Issued items (cop loadout) are never lootable and never shown in a body search
- `sell_multiplier() = 1.0 + min(notoriety / 10000.0, 1.5)` (max 2.5x)
- **Notoriety resets** on death, surrender, or a successful sale at `Center` (`server_sell_loot()`).
  Extraction alone does not reset it, so the player can still cash in the multiplier.
- `server_sell_loot()` applies the multiplier to the bag value, adds `cash`, clears the bag, and resets notoriety

### 8.1 Surrender

- Requestable only as `CRIMINAL` in `LootyBay`
- The server looks for a `COP` in the same instance within `6` m with line of sight
  (raycast in the instance world)
- The cop receives `50%` of the `loot_bag` value as a cash reward (`SURRENDER_COP_REWARD_RATIO`)
- `loot_bag` is cleared, `equipped_gear` is kept, role becomes `CITIZEN`, notoriety resets, and the
  player is transferred to `Motel`

### 8.2 Death

| Role at death | LootDrop | Inventory after respawn | Role after respawn |
|---|---|---|---|
| `CITIZEN` | none | everything kept | `CITIZEN` |
| `CRIMINAL` | all of `loot_bag` + `equipped_gear` | both cleared | `CITIZEN` |
| `COP` | `loot_bag` + non-issued gear; issued items are destroyed, never dropped | everything cleared, off duty | `CITIZEN` |

In every case the player respawns at `Motel`, notoriety resets, and `life_state` returns to `ALIVE`
with full HP. The `LootDrop` is created at the death position in the original instance before
despawn; a body whose items were all taken while downed produces no empty drop.

Order on `DEAD`: cancel channels where the player is actor or target → close search sessions (body
or viewer) → create the `LootDrop` → despawn/transfer on `call_deferred`. Despawning never happens
inside a `life_state_changed` handler. `PlayerService.handle_player_death()` applies the outcome and
defers the Motel transfer; `PlayerService.handle_peer_left()` resolves a downed body's death and
LootDrop synchronously before `detach_peer()`.

### 8.3 Extraction

When a player enters the `LootyBay` `ExtractZone` (detected by the server through `Area3D`):

- Extraction requires `ALIVE`; the deferred handler re-checks it, so a downed body cannot extract
- After a revive inside the zone, `DownedService` re-checks `ExtractZone.get_overlapping_bodies()`
  (no new `body_entered` fires) and runs extraction if the player stands inside
- `CITIZEN` → transferred to `Motel`
- `CRIMINAL` → role becomes `CITIZEN` (this is the successful extraction), then `Motel`
- `COP` → goes off duty (gear restored), then `Motel`

## 9. Lootable and LootDrop

### 9.1 Lootable

`features/heist/Lootable.gd` is a server-authoritative container (`@export value`, `locked`):

- `server_lockpick(player)` is silent: no alert
- `server_smash(player)` is loud: alerts the `COP` and `CRIMINAL` members of the same instance through
  `Instance.rpc_to_specific_members()`, including `global_position`
- Checks that the player is in the same instance as the lootable and that it has not been looted yet

### 9.2 LootDrop

`features/heist/LootDrop.gd` holds the dead player's `loot_items` + `gear_items` through a
`features/heist/LootContainer.gd` (items, viewers, take-by-uid, injected `can_access` / `on_take`).

- The server creates the real node under `<instance>/Drops`; contents stay server-side
- `client_add_loot_drop` / `sync_state_to_peer` mirror only the drop id and position (a visual
  placeholder); no item lists are ever sent
- Clients that join the instance later receive existing drops through `sync_state_to_peer()`
- When a drop is emptied the server calls `client_remove_loot_drop` and frees the node

## 10. Map placeholders

- `maps/motel/Motel.tscn`: floor, 16 `SpawnPoints`, `CashStash`, `PartyDesk`
- `maps/looty_bay/LootyBay.tscn`: floor + walls, 12 spawn points, `ExtractZone`, `PoliceStation`,
  `PoliceVehicle` (hidden until a cop is on duty)
- `maps/house/House.tscn`: floor, 6 spawn points, `Storage`, `LaundryDesk`
- `maps/center/Center.tscn`: floor, 6 spawn points, market stalls, `UpgradeBench`

`Instance.setup()` instantiates the map scene as a child named `Map`, then finds `ExtractZone` /
`PoliceStation` on the server only to connect `body_entered` / `body_exited`.

## 11. Client controls (temporary, for testing)

Every action key targets the nearest other player in the current instance.

- `1` = Motel, `2` = LootyBay, `3` = House, `4` = Center
- `5` = sell loot (must be in Center)
- `F` = request mask
- `G` = toggle cop duty
- `H` = surrender
- `P` = create party
- `R` = revive target, `X` = finish target, `C` = cuff target
- `E` = open body search (contents are printed), `T` = take first listed item, `Q` = close search
- `K` = attack target (`request_attack`)
- WASD = movement (client sends `server_request_move` to the server)
- The client prints its own life state and bleed-out seconds whenever they change

## 12. Running and testing

Server:

```text
godot_console --headless --path . -- --server
```

Client (connects to `127.0.0.1:7777`):

```text
godot_console --path .
```

Headless test suite (no network needed):

```text
godot_console --headless --path . -s res://tests/run_tests.gd
```

`tests/run_tests.gd` discovers every `tests/**/test_*.gd`, runs each zero-argument `test_*` method
through the shared `tests/TestCase.gd` assertions, prints per-file results, then prints
`ALL TESTS PASSED (<n> assertions)` and calls `quit(0)`; any failure calls `quit(1)`.

Coverage mirrors the source tree: server id format (`tests/autoload/`), party max 3 and leader
transfer (`tests/features/party/`), instance selection and id format
(`tests/features/instance/`), the `can_attack` matrix including real `Player` node shapes and
